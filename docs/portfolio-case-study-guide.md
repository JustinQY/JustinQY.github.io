# 作品集案例：文章结构与表达指南

以 Curam → FHIR 案例为基础，结合招聘者浏览反馈整理。后续政府数据工程、AI 和 iOS 项目沿用这套阅读顺序与视觉设计，具体技术小节按项目调整。

## 核心原则

读者应能快速回答四个问题：项目解决什么问题、原来难在哪里、我做了什么、设计带来什么价值。先说明业务任务和输入 / 输出，再介绍技术；把设计机制与收益连接起来，避免只列工具名称。

页面使用英文，指南与审核笔记可用中文。正文以短段落、短表格和一张流程图为主，一般约 500–800 英文词（含短表格，不含图中文字）；清楚优先，不为了凑字数补段落。

## 默认文章结构

| 顺序 | 小节                         | 应回答的问题与建议内容                                                                                                                                           |
| ---- | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | At a glance                  | 为谁做、解决什么任务、输入 / 输出是什么、个人职责和实际项目时间。用一句业务说明加一句方案概述，配 2–3 项有依据的成果。                                           |
| 2    | The challenge                | 原有方法遇到什么困难、规模或约束如何放大问题。说明真实场景，避免只讲技术概念。                                                                                   |
| 3    | My contribution              | 我亲自设计 / 实现 / 验证了哪些部分，谁负责业务审核。职责或模块分工可用短表格，不把团队全部成果归到个人。                                                         |
| 4    | How the workflow works       | 一张简洁流程图解释输入 → 处理 → 校验 → 输出。标清自动步骤、人工步骤、循环与失败暂停；补一小段说明即可。                                                          |
| 5    | 项目的核心设计小节           | 选择最有代表性的 2–3 项机制，说明“困难 → 设计 → 作用”。FHIR 案例用 Skills that guide the reasoning；iOS 可用 Key engineering decisions，聚焦架构、性能或可靠性。 |
| 6    | Evaluation and quality gates | 如何检查结果，规则检查、语义 / 功能复核和业务评价分别能证明什么。说明一个主要验证边界，详细审计留在独立文档。                                                    |
| 7    | Results and business value   | 展示真实指标、采用情况与交付物；说明统计单位、范围和含义。截图或表格紧跟对应结论。                                                                               |
| 8    | What I learned               | 一项有价值的设计经验，以及 1–2 项具体后续改进。将已实现与计划分开。                                                                                              |
| 9    | Source and standard          | 相关源码、标准或演示入口。重要代码分析可引用固定提交；交付经历与公开仓库能证明的事实分别表述。                                                                   |

有真实记录时，增加一个很短的代表性案例：输入 / 业务含义 → 原问题 → 规则或评估如何发现问题 → 最终方案及理由。它可以嵌入核心设计或评估小节，不必增加独立大章节。没有实际记录时，不编造“错误被发现”的过程。

## 从本篇得到的表达经验

- **业务目标先于框架名称。** Curam、FHIR、BA、内部缩写首次出现时，给外部读者足够的业务解释；还要说明结果帮助团队完成什么工作或决策。
- **职责分工要具体。** “采用 multi-agent”应展开为谁做什么、交付什么、谁能批准 / 阻止推进。不要把脚本、Skill 和 subagent 混为一类。
- **从特点写到价值。** 例如批次拆分帮助定位问题，Skills 固化判断依据，独立 reviewer 挑战生成结果，进度记录支撑恢复。机制支持的作用与测量得到的提升分开。
- **评估应分层。** 规则校验通过不等于业务正确；AI reviewer 不等于人类专家基准；BA usefulness 不等于 FHIR conformance。其他项目也要解释指标究竟衡量什么。
- **量化结论需要定义。** 写清按表 / 字段 / 映射项统计、全量还是抽样、何为有效，以及是否允许修改后采用。没有时间、成本或 baseline 测量就不补数字。
- **设计意图不写成已证实效果。** 可以写“旨在减少无依据输出”，不能在缺少对照时声称“消除幻觉”“达到高级 BA 水准”或量化优于单 prompt。
- **少重复，多证据。** 概览只保留关键成果，正文用一张流程图讲协作，用短表格讲职责 / 规则 / 评估，用真实截图讲交付。删除功能清单与流程图的重复介绍。
- **展示状态与事实分开。** 使用源码、本人确认和真实产物交叉核对；公开快照未包含内部交付物时，不擅自判断项目没有完成。

## 延续现有视觉设计

- Back to projects 位于主标题上方。
- 描述位于主标题下方、技术标签上方，保持左对齐。
- 详情页使用宽正文与右侧目录；小屏幕使用正文内目录。
- 核心成果优先展示；Source code / 标准链接及分隔线紧跟成果模块。
- 流程图沿用站点字体、纸面背景和绿色强调色；手机端纵向排列，图中不把人工步骤误画为自动步骤。
- 真实成果图片支持放大；表格在小屏幕上保持可读，不造成整个页面横向溢出。
- 完成的 case-study 卡片不显示顶部编号或状态；尚未完成的预留卡片继续显示 Coming soon。技术 notes 保留自身标签。

## 新项目开始前收集

1. 业务背景、实际使用者、原有方法及主要痛点。
2. 输入、输出、项目阶段、个人职责与时间。
3. 关键设计及其对应的困难；一个可展示的真实案例（如有）。
4. 验证方式、指标定义、实际结果与采用情况。
5. 可公开的源码、架构图、截图或交付摘要。

先完成有依据的内容，再明确列出待确认项；不要把未知事实写成肯定结论。审核完成后将项目标记为完成，未完成项目保留预留状态。
